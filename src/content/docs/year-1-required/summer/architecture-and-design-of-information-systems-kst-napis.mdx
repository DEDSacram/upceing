## Week 1: Enterprise Architecture — Concepts, Goals, Methods

Enterprise architecture aligns business strategy with IT landscape. Frameworks like TOGAF ADM and Zachman organize the work from principles to governed change. This week sets vocabulary and method.

### Key Concepts

- **EA domains:** business, data, application, technology (+ security).
- **Goals:** transparency, standardization, agility, cost control, risk reduction.
- **TOGAF ADM:** vision → business → IS → technology → opportunities → migration → governance.

| Framework | Idea | Strength |
|-----------|------|----------|
| TOGAF | ADM cycle + content metamodel | Process-heavy, complete |
| Zachman | 6×6 interrogative matrix | Taxonomy clarity |
| ArchiMate | Visual EA language | Communicable models |

```text
Example principle:
  P-03 "Cloud-first, but data stays in EU."
  Rationale: elasticity + GDPR. Implication: vet every SaaS for residency.
```

> **Rule:** Every architecture decision needs rationale + implication — otherwise it is decoration.

## Week 2: ArchiMate Language Basics

ArchiMate models active structure, behavior, and passive structure across three core layers plus motivation and implementation extensions. Relations (serving, realization, assignment, aggregation) carry the meaning.

### Layers at a Glance

| Layer | Active | Behavior | Passive |
|-------|--------|----------|---------|
| Business | Actor, Role | Process, Function | Business Object |
| Application | Component | Service, Function | Data Object |
| Technology | Node, Device | Service, Function | Artifact |

### Relations Mini-Guide

```text
Serving:      A ----> B   (A serves B, arrow to user)
Realization:  A - - |> B   (A realizes B, e.g. process realizes service)
Assignment:   A ---● B    (responsibility: role assigned to process)
Aggregation:  A <>--- B   (whole-part)
```

## Week 3: Types of Architectural Views

A view is a projection for a stakeholder concern; a viewpoint is the template. Good architects maintain traceability from motivation (goals, requirements) down to physical deployment without mixing abstraction levels.

### Viewpoint Catalog

| Viewpoint | Audience | Shows |
|-----------|----------|-------|
| Organization | Management | Actors, roles, locations |
| Business process | Process owners | Flows, objects, services |
| Application cooperation | App owners | Components + interfaces |
| Technology usage | Ops | Nodes, artifacts, networks |
| Migration | Board | Plateaus, gaps, work packages |

```yaml
# viewpoint definition sketch
viewpoint: application-usage
stakeholders: [CIO, app-owner]
concerns: [overlap, licensing-cost]
elements: [application-component, application-service, data-object]
```

## Week 4: Software Quality Requirements and Measurement

Quality requirements are measurable constraints (ISO/IEC 25010: performance, reliability, security, maintainability...). Architecture must turn vague "-ilities" into scenarios with stimulus, response, and measure — then design tactics to satisfy them.

### Quality Scenario Template

| Field | Example |
|-------|---------|
| Stimulus | 1000 concurrent checkouts |
| Response | P95 < 2 s, no errors |
| Tactic | Cache, autoscale, async queue |
| Metric | APM p95, error budget burn |

### Tactics Sampler

```text
Availability:  ping/echo, active redundancy, spare, rollback.
Performance:   caching, pooling, load balancing, CQRS read models.
Security:      authenticate, authorize, encrypt, audit.
Modifiability: encapsulation, interfaces, publish-subscribe, config-as-code.
```

## Week 5: Application Portfolio Analysis

Portfolios drift: duplicates,Zombie apps, shadow IT. TIME (Tolerate, Invest, Migrate, Eliminate) plus business-fit/technical-fit scoring rationalizes the landscape into invest/divest roadmaps.

### TIME Model

| Quadrant | Action | Example |
|----------|--------|---------|
| Invest | Standardize, scale | Core ERP |
| Migrate | Replatform/replace | Legacy billing → SaaS |
| Tolerate | Contain cost | Niche lab tool |
| Eliminate | Retire | Duplicate reporting |

```text
Scoring (1-5): businessFit, techFit, cost/yr, risk.
  Eliminate candidates: businessFit ≤ 2 AND techFit ≤ 2.
  Migrate candidates:   businessFit ≥ 4 AND techFit ≤ 2.
```

## Week 6: Architecture and Solution Building Blocks

TOGAF distinguishes Architecture Building Blocks (ABB — reusable specifications) from Solution Building Blocks (SBB — concrete products/instances). Catalogs, interfaces, and compliance keep reuse real instead of slideware.

### ABB vs SBB

| Aspect | ABB | SBB |
|--------|-----|-----|
| Nature | Spec, pattern | Product, instance |
| Example | "SSO service spec" | Keycloak v22 @ SSO-cluster |
| Reuse | Reference | Deploy |
| Governed by | Standards board | Change + ops |

```yaml
abb:
  id: ABB-AUTH-01
  name: Central Authentication
  standards: [OIDC, SAML2]
  interfaces: [login, token-refresh, logout]
sbb:
  id: SBB-AUTH-KEYCLOAK
  implements: ABB-AUTH-01
  version: "22.0"
  sla: "99.9%"
```

## Week 7: BPMN Business Process Modelling in Camunda

BPMN 2.0 executable processes connect business flows to software: start events, user/service tasks, exclusive/parallel gateways, boundary timers. Camunda adds FEEL/DMN, external tasks, and Cockpit monitoring.

### Core Symbols

| Symbol | Use |
|--------|-----|
| Start / End event | Process boundaries |
| User task | Human form step |
| Service task | Code/connector call |
| Exclusive gateway `×` | If/else branch |
| Parallel gateway `+` | Fork/join |

### Executable Snippet

```xml
<!-- Camunda BPMN excerpt: order approval -->
<serviceTask id="checkStock" name="Check stock"
  camunda:type="external" camunda:topic="stock-check" />
<exclusiveGateway id="inStock" name="In stock?" />
<sequenceFlow sourceRef="inStock" targetRef="ship">
  <conditionExpression xsi:type="tFormalExpression">${stockOk}</conditionExpression>
</sequenceFlow>
<userTask id="approve" name="Manager approval"
  camunda:assignee="${manager}" camunda:dueDate="P2D" />
```

## Week 8: Building Applications from Solution Building Blocks

Composable applications assemble SBBs through contracts: API gateways, events, shared identity. Integration styles (sync REST, async messaging, file/ETL) trade coupling for autonomy — choose per quality scenario.

### Integration Matrix

| Style | Coupling | When |
|-------|----------|------|
| REST sync | Temporal | Query, low latency |
| Events/async | Decoupled | Notifications, sagas |
| ETL/batch | Loose, stale | Reporting, migration |

## Week 9: Agile Methods in the Enterprise Context

Enterprise agility scales Scrum with architecture runway, PI planning, and lean governance. Intentional architecture (emergent + planned) prevents both big-upfront-design stall and integration chaos.

### Scaling Elements

| Element | Purpose |
|---------|---------|
| Epic → Feature → Story | Portfolio to team backlog |
| Architecture runway | Just-enough enablers ahead |
| PI planning (SAFe) | Cross-team dependency sync |
| Lean business case | Fund epics by WSJF |

```text
WSJF = Cost of Delay / Job Size.  Highest first.
Enabler example: "API gateway mTLS" as runway before "partner onboarding".
```

> **Rule:** If the runway is empty, teams build on sand; if it is a highway, you rebuilt waterfall.

## Week 10: Architecture and Project Preparation

Architecture feeds project charters: scope, constraints, risks, estimates, and decision logs (ADR). RACI plus stage gates keep sponsors, architects, and delivery aligned from initiation to transition.

### Charter Checklist

```markdown

- Scope in/out, constraints, assumptions
- Risks (top 5 + owners)
- Milestones, budget envelope
```

## Week 12: Typical Ecosystem Transformation Problems

Transformations fail on data, coupling, and people — not diagrams. Strangler fig, anti-corruption layer, data migration (expand–migrate–contract), and parallel runs de-risk the cutover.

### Problem → Pattern

| Problem | Pattern | Note |
|---------|---------|------|
| Big-bang fear | Strangler fig | Route incrementally |
| Legacy model leaks | Anti-corruption layer | Translate at boundary |
| Downtime migration | Expand–migrate–contract | Dual-write then switch |
| Silent regression | Parallel run / shadow | Compare outputs |

```text
Strangler route example (gateway):
  /billing/* --10%--> new-billing, --90%--> legacy
  promote % weekly on error-budget signal.
```

## Week 13: Service-Oriented Architectures

SOA (and its microservice descendant) structures capabilities as governed services with explicit contracts, registries, and policies. REST, events, and (where needed) SOAP/ESB each fit different coupling and governance needs.

### SOA Checklist

| Concern | Solution |
|---------|----------|
| Contract | OpenAPI / AsyncAPI, versioning |
| Discovery | Registry, gateway routing |
| Security | OAuth2/OIDC, mTLS, scopes |
| Resilience | Timeout, retry+backoff, circuit breaker |
| Observability | Trace IDs, SLO dashboards |

```yaml
# service contract fragment (AsyncAPI)
channels:
  order.created:
    subscribe:
      message: {payload: {type: object, properties: {orderId: {type: string}}}}
```

## Code Review Guide

### What to Look For

#### 1. Model hygiene
- Element types correct per layer? Relations legal in ArchiMate?

#### 2. Traceability
- Requirement → process → service → component → node unbroken?

#### 3. Executability
- BPMN has no dead ends, gateways balanced, service topics bound?

<div class="review-note">

<strong>🔍 Practice Review:</strong> A BPMN has an exclusive gateway with 3 outgoing flows but only 1 condition, plus a service task with no topic. Issues: default flow missing, unbound connector, no error boundary. Fix: add default flow + conditions on all, bind `camunda:topic`, add error end event and retry policy.

```xml
<!-- fixed gateway -->
<exclusiveGateway id="g1" />
<sequenceFlow id="f1" sourceRef="g1" targetRef="a">
  <conditionExpression>${approved}</conditionExpression>
</sequenceFlow>
<sequenceFlow id="default" sourceRef="g1" targetRef="b" />
```

## Quick Reference Cards

### ArchiMate Relations

```text
Serving      A ------> B     (used by)
Realization  A - - - |> B    (implements)
Assignment   A -------● B    (does)
Aggregation  A <>------ B    (has)
Composition  A <#>------ B   (owns)
Triggering   A ---|> B       (causes, hollow arrow)
```

### BPMN Essentials

| Element | Pitfall | Fix |
|---------|---------|-----|
| Exclusive gateway | Missing default | Always add default flow |
| Service task | No topic/connector | Bind type + topic |
| Timer boundary | No escalation path | Link to escalate task |
| Parallel gateway | Unbalanced fork/join | Pair every fork |


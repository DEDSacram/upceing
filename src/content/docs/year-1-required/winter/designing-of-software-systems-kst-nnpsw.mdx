## Week 1: Introduction to Software Engineering

This week provides historical context and introduces the fundamental principles of software engineering that underpin modern system design.

### Historical Evolution of Software Engineering

**The Software Crisis (1960s-1970s):**
- Projects running over budget and schedule
- Low-quality software with numerous defects
- Difficulty in maintaining and evolving systems

**Key Milestones:**
- 1968: NATO Software Engineering Conference
- 1970s: Waterfall model
- 1980s: Object-oriented programming
- 1990s: UML and Unified Process
- 2000s: Agile methodologies
- 2010s: DevOps and continuous delivery

### What is Software Engineering?

Software engineering is the application of engineering principles to software development:

1. **Systematic approach** - disciplined methodologies and processes
2. **Quantifiable** - measurable outcomes and progress
3. **Economic** - cost-effective solutions
4. **Quality focus** - reliability, maintainability, usability

```java
// Example: A well-structured Java class demonstrating design principles
public class BankAccount {
    // Encapsulation - private fields
    private String accountNumber;
    private double balance;
    private String ownerName;
    
    // Constructor
    public BankAccount(String accountNumber, String ownerName) {
        this.accountNumber = accountNumber;
        this.ownerName = ownerName;
        this.balance = 0.0;
    }
    
    // Public interface - well-defined methods
    public void deposit(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Deposit amount must be positive");
        }
        this.balance += amount;
    }
    
    public boolean withdraw(double amount) {
        if (amount <= 0 || amount > balance) {
            return false;
        }
        this.balance -= amount;
        return true;
    }
    
    public double getBalance() {
        return balance;
    }
}
```

### Key Principles

**The "No Silver Bullet" Concept (Brooks, 1986):**
- No single technology can solve all software problems
- Essential complexity is inherent
- Accidental complexity can be reduced

**Separation of Concerns:**
- Divide complex systems into manageable parts
- Each part addresses a specific concern
- Reduces cognitive load and improves maintainability

## Week 2: Development Methodologies

This week covers the spectrum of software development methodologies from traditional to agile approaches.

### The Unified Process (UP)

**Characteristics:**
- Iterative and incremental
- Use case driven
- Architecture-centric
- Risk-focused

**Phases of UP:**

| Phase | Purpose | Key Activities |
|-------|---------|----------------|
| Inception | Establish scope | Vision, feasibility, business case |
| Elaboration | Plan architecture | Detailed requirements, architectural baseline |
| Construction | Build product | Incremental development, testing |
| Transition | Deploy system | User training, deployment, maintenance |

**Core Workflows:**
1. Business Modeling
2. Requirements
3. Analysis & Design
4. Implementation
5. Test
6. Deployment
7. Configuration & Change Management
8. Project Management
9. Environment

### Agile Methodologies

**Agile Manifesto (2001):**
- Individuals and interactions over processes and tools
- Working software over comprehensive documentation
- Customer collaboration over contract negotiation
- Responding to change over following a plan

**Scrum Framework:**
- **Roles:** Product Owner, Scrum Master, Development Team
- **Artifacts:** Product Backlog, Sprint Backlog, Increment
- **Events:** Sprint Planning, Daily Scrum, Sprint Review, Sprint Retrospective

**Comparison of Methodologies:**

| Aspect | Unified Process | Agile (Scrum) |
|--------|-----------------|---------------|
| Approach | Predictive | Adaptive |
| Planning | Detailed upfront | Continuous |
| Documentation | Comprehensive | Minimal/just-in-time |
| Customer involvement | Milestone-based | Continuous |
| Team structure | Hierarchical | Self-organizing |
| Focus | Architecture | Delivering value |

## Week 3: Requirements Engineering

Requirements engineering is the foundation of successful software development. This week focuses on finding and specifying requirements.

### Types of Requirements

**Functional Requirements:**
- What the system should do
- Specific behaviors and functions
- Example: "The system shall allow users to reset their password"

**Non-functional Requirements:**
- How the system should perform
- Quality attributes and constraints
- Categories:
  - Performance: response time, throughput
  - Security: authentication, authorization
  - Usability: user interface, accessibility
  - Reliability: availability, fault tolerance
  - Maintainability: modularity, testability
  - Portability: platform compatibility

### Requirements Elicitation Techniques

**Interviews:**
- Structured vs. unstructured
- Individual vs. group
- Active listening and probing

**Workshops:**
- Joint Application Development (JAD)
- Facilitated sessions with stakeholders
- Rapid requirements gathering

**Observation:**
- Contextual inquiry
- Shadowing users
- Understanding workflows

**Prototyping:**
- Low-fi (paper, wireframes)
- High-fi (interactive mockups)
- Validate understanding early

### Requirements Specification

**IEEE 830 Standard Structure:**
1. Introduction
2. General Description
3. Specific Requirements
4. Appendices

**Writing Quality Requirements:**
- **C**orrect - accurate and truthful
- **U**nambiguous - clear and precise
- **C**omplete - includes all necessary information
- **C**onsistent - no contradictions
- **V**erifiable - testable
- **R**ankable - prioritized
- **T**raceable - linked to source

```yaml
# Example: Requirements specification in YAML format
functional_requirements:
  - id: FR-001
    title: User Registration
    description: New users can register with email and password
    priority: High
    status: Approved
  
  - id: FR-002
    title: User Login
    description: Registered users can log in using email and password
    priority: High
    status: Approved
    dependencies:
      - FR-001
  
  - id: FR-003
    title: Password Reset
    description: Users can reset forgotten password via email
    priority: Medium
    status: Draft

non_functional_requirements:
  - id: NFR-001
    category: Performance
    description: Response time must be under 2 seconds for 95% of requests
    metric: Response time < 2s for 95th percentile
  
  - id: NFR-002
    category: Security
    description: All passwords must be encrypted using bcrypt
    metric: Passwords stored with bcrypt hash

  - id: NFR-003
    category: Availability
    description: System must be available 99.9% of the time
    metric: Uptime ≥ 99.9% annually
```

## Week 4: Use Case Modeling Fundamentals

Use case modeling captures functional requirements from the user's perspective, forming the foundation for system design.

### What is a Use Case?

A **use case** describes a sequence of actions that a system performs to produce a measurable result of value to an actor.

**Components:**
- **Actor:** External entity interacting with the system (person, system, hardware)
- **Use Case:** Goal-oriented functionality
- **Relationship:** Association between actor and use case

### Creating Use Cases

**Use Case Template:**

| Element | Description |
|---------|-------------|
| Name | Unique identifier and descriptive name |
| ID | Unique number for traceability |
| Actor(s) | Primary and secondary actors |
| Brief Description | One-sentence summary |
| Preconditions | State before the use case starts |
| Flow of Events | Step-by-step interaction |
| Alternative Flows | Variations and exceptions |
| Postconditions | State after the use case completes |

### Use Case Diagram

The use case diagram provides a high-level view of system functionality:

```
┌─────────────────────────────────────┐
│           Online Bookstore          │
│                                     │
│  ┌───────────┐    ┌──────────┐     │
│  │  Customer  │───▶│   Browse │     │
│  └───────────┘    └──────────┘     │
│       │            ┌──────────┐     │
│       └───────────▶│ Search   │     │
│                    └──────────┘     │
│                    ┌──────────┐     │
│                    │ Purchase │◀────┐
│                    └──────────┘     │
│                    ┌──────────┐     │
│                    │ Register │◀────┤  ┌────────┐
│                    └──────────┘     │  │ Admin  │
│                    ┌──────────┐     │  └────────┘
│                    │ Login    │◀────┘
│                    └──────────┘
└─────────────────────────────────────┘
```

```yaml
# Example: Use case specification in YAML
use_case:
  id: UC-004
  name: Purchase Books
  actor:
```

## Week 5: Advanced Use Case Modeling

This week explores advanced use case concepts including include, extend, and generalization relationships.

### Use Case Relationships

**Include Relationship (`<<include>>`):**
- Mandatory sub-flow
- Used to factor out common behavior
- "Always executes" as part of base use case
- Example: `Login` is included in `Purchase Books`

**Extend Relationship (`<<extend>>`):**
- Optional behavior
- Adds functionality under certain conditions
- "May execute" based on extension points
- Example: `Apply Discount` extends `Purchase Books`

**Generalization:**
- Inheritance relationship between use cases
- Child use case inherits parent's behavior
- Can override or extend parent's behavior

```
┌─────────────────────────────────────────────────────┐
│  <<include>>      ┌─────────────┐                  │
│  ┌─────────────┐  │   Purchase   │                  │
│  │   Login     │──│   Books     │                  │
│  └─────────────┘  └─────────────┘                  │
│                          │                         │
│                          │ <<extend>>              │
│                          ▼                         │
│                     ┌─────────────┐                │
│                     │   Apply     │                │
│                     │  Discount   │                │
│                     └─────────────┘                │
│                          │                         │
│                          │ Generalization          │
│                          ▼                         │
│                     ┌─────────────┐                │
│                     │   Express   │                │
│                     │  Purchase   │                │
│                     └─────────────┘                │
└─────────────────────────────────────────────────────┘
```

### Extension Points

Extension points define where an extending use case can be inserted:

```java
// Example: Use case with extension points in code
public class PurchaseBooks {
    // Extension point: apply discount before payment
    @ExtensionPoint("BeforePayment")
    public void beforePayment() {
        // Standard behavior
    }
    
    @ExtensionPoint("BeforePayment")
    public void applyDiscount() {
        // Extending behavior
        // Check for applicable discounts
        // Apply discount to order total
    }
}
```

### Use Case Documentation Best Practices

1. **Level of Detail:** Vary detail based on importance and risk
2. **Actor Goals:** Focus on business value
3. **Technology Neutral:** Avoid implementation details
4. **Clear Language:** Write for all stakeholders
5. **Consistent Structure:** Use templates

## Week 6: Analysis and Design Fundamentals

This week covers the transition from analysis to design, introducing the concept of architectural layers and design principles.

### Analysis vs. Design

| Aspect | Analysis | Design |
|--------|----------|--------|
| Focus | What the system should do | How the system will do it |
| Perspective | Problem domain | Solution domain |
| Models | Conceptual, platform-independent | Detailed, platform-specific |
| Level | High-level understanding | Implementation details |
| Audience | Domain experts, stakeholders | Developers, architects |

### The Four-Layer Architecture

**Layer 1: User Interface (UI)**
- Presentation of information
- User interaction handling
- Input validation at the boundary

**Layer 2: Application Logic (Business Logic)**
- Domain rules and policies
- Workflow management
- Use case implementation

**Layer 3: Domain Model**
- Core business objects
- Business relationships
- Business rules

**Layer 4: Technical Services (Persistence, Communication)**
- Database access
- External system integration
- Infrastructure services

```java
// Example: Layered architecture implementation
// Layer 4: Technical Services
public class BookRepository {
    private JdbcTemplate jdbcTemplate;
    
    public Book findById(Long id) {
        // Database access code
    }
}

// Layer 3: Domain Model
public class Book {
    private Long id;
    private String title;
    private String author;
    private ISBN isbn;
    private Money price;
    private int stockQuantity;
    
    // Domain methods
}

// Layer 2: Application Logic
public class OrderService {
    private BookRepository bookRepository;
    private OrderRepository orderRepository;
    
    @Transactional
    public Order createOrder(OrderRequest request) {
        // Business logic - orchestrating domain objects
    }
}

// Layer 1: User Interface
@RestController
public class OrderController {
    private OrderService orderService;
    
    @PostMapping("/api/orders")
    public ResponseEntity<Order> createOrder(@RequestBody OrderRequest request) {
        // HTTP handling and input validation
    }
}
```

### Design Principles

**GRASP Principles:**
- Information Expert
- Creator
- Controller
- Low Coupling
- High Cohesion
- Polymorphism
- Pure Fabrication
- Indirection
- Protected Variations

## Week 7: Classes and Objects

This week covers the fundamental concepts of object-oriented modeling - classes and objects.

### Understanding Classes

A **class** is a template that describes the state and behavior of objects.

**Components of a Class:**
- **Name:** Unique identifier
- **Attributes:** Data or state
- **Methods:** Behavior or operations

**Visibility:**
- `+` Public: Accessible to all
- `-` Private: Accessible only within the class
- `#` Protected: Accessible to subclasses
- `~` Package: Accessible within the package

### UML Class Notation

```
┌─────────────────────────────┐
│          Order               │
├─────────────────────────────┤
│ - orderNumber: String       │
│ - orderDate: Date           │
│ - status: OrderStatus       │
│ - totalAmount: Money        │
├─────────────────────────────┤
│ + createOrder()             │
│ + addItem(Item)             │
│ + removeItem(Item)          │
│ + calculateTotal()          │
│ + changeStatus(Status)      │
└─────────────────────────────┘
```

### Object State

An **object** is an instance of a class with specific state:

```java
// Class definition
public class Order {
    private String orderNumber;
    private Date orderDate;
    private OrderStatus status;
    private List<OrderItem> items;
    private Money totalAmount;
    
    public Order(String orderNumber) {
        this.orderNumber = orderNumber;
        this.orderDate = new Date();
        this.status = OrderStatus.NEW;
        this.items = new ArrayList<>();
        this.totalAmount = Money.zero();
    }
    
    public void addItem(Item item) {
        items.add(new OrderItem(item));
        recalculateTotal();
    }
    
    private void recalculateTotal() {
        totalAmount = items.stream()
            .map(OrderItem::calculateSubtotal)
            .reduce(Money.zero(), Money::add);
    }
}

// Object creation and use
Order order = new Order("ORD-2024-001");
order.addItem(new Book("Design Patterns", 49.99));
order.addItem(new Book("Clean Code", 39.99));
System.out.println(order.getTotalAmount());
```

### Object-Oriented Principles

**Encapsulation:**
- Bundle data and methods together
- Hide internal state
- Provide controlled access

**Abstraction:**
- Focus on essential features
- Hide implementation details
- Provide simple interfaces

## Week 8: Identifying Analytical Classes

This week focuses on discovering classes from requirements and use cases.

### Methods for Finding Classes

**Noun Extraction (Textual Analysis):**
- Read requirements documents
- Underline nouns and noun phrases
- Classify as likely classes, attributes, or relationships

**CRC Cards (Class-Responsibility-Collaboration):**
- **Class:** What is the class name?
- **Responsibilities:** What does it know and do?
- **Collaborators:** Who does it work with?

**Use Case Analysis:**
- Look for nouns in use case descriptions
- Identify boundaries and interfaces
- Find entities that persist

### CRC Card Example

```
┌─────────────────────────────────┐
│        Class: Order             │
├─────────────────────────────────┤
│ Responsibilities:               │
│ - Knows its items and totals    │
│ - Calculates order total        │
│ - Manages order status          │
│ - Validates order data          │
├─────────────────────────────────┤
│ Collaborators:                  │
│ - Customer                      │
│ - OrderItem                     │
│ - Payment                       │
│ - Inventory                     │
└─────────────────────────────────┘
```

### Identifying Abstraction Boundaries

**Guidelines for Class Selection:**
1. **Significance:** Does it represent an important concept?
2. **State:** Does it have significant state to track?
3. **Behavior:** Does it have distinct behavior?
4. **Identity:** Can we distinguish instances?
5. **Independence:** Can it exist independently?

## Week 9: Class Relationships

This week explores the fundamental relationships between classes in object-oriented design.

### Association

A **association** is a relationship where one class knows about another.

**Multiplicity:**
- 1: Exactly one
- * (0..*): Zero or more
- 1..*: One or more
- 0..1: Zero or one
- m..n: Range from m to n

### Aggregation and Composition

**Aggregation (`<>`):**
- "Has-a" relationship
- Part can exist independently of the whole
- Weak ownership
- Example: Department has Employees (employee can exist without department)

**Composition (`<*>`):**
- "Contains" relationship
- Part cannot exist without the whole
- Strong ownership
- Example: Order contains OrderLines (lines cannot exist without order)

```
┌──────────────┐     ┌──────────────┐
│   Order      │▸---▶│  OrderLine   │
├──────────────┤ 1  *├──────────────┤
│ - orderNumber│     │ - quantity   │
│ - orderDate  │     │ - unitPrice  │
│ - status     │     │ - lineTotal  │
└──────────────┘     └──────────────┘
        │                    │
        │ 1                  │ 1
        │                    │
        ▼ 0..1               ▼
┌──────────────┐     ┌──────────────┐
│  Customer    │     │   Product    │
├──────────────┤     ├──────────────┤
│ - name       │     │ - name       │
│ - email      │     │ - description│
│ - address    │     │ - price      │
└──────────────┘     │ - stock      │
                     └──────────────┘
```

```java
// Java implementation of relationships
public class Order {
    // Composition: OrderLine cannot exist without Order
    private List<OrderLine> lines; 
    
    // Association: Customer can exist independently
    private Customer customer;
    
    public void addLine(Product product, int quantity) {
        OrderLine line = new OrderLine(product, quantity);
        lines.add(line);
    }
}

public class OrderLine {
    // Association: Product exists independently
    private Product product;
    private int quantity;
    private Money lineTotal;
    
    public OrderLine(Product product, int quantity) {
        this.product = product;
        this.quantity = quantity;
        this.lineTotal = product.getPrice().multiply(quantity);
    }
}

public class Customer {
    private CustomerId id;
    private Name name;
    private Email email;
    private List<Order> orderHistory;
}
```

## Week 10: Inheritance and Polymorphism

This week covers inheritance and polymorphism, two key pillars of object-oriented design.

### Inheritance (`<>`)

Inheritance represents an "is-a" relationship where a subclass inherits from a superclass.

**Benefits:**
- Code reuse
- Polymorphism
- Extensibility

**Drawbacks:**
- Tight coupling
- Fragile base class problem
- Deep hierarchies can be complex

```
┌─────────────────────────────┐
│      BaseEntity             │
├─────────────────────────────┤
│ - id: Long                  │
│ - createdAt: Date           │
│ - updatedAt: Date           │
├─────────────────────────────┤
│ + getId(): Long             │
│ + getCreatedAt(): Date      │
│ + getUpdatedAt(): Date      │
└─────────────────────────────┘
           ▲
           │
           ├──────────────────────┐
           │                      │
┌──────────┴──────────┐ ┌────────┴──────────┐
│    User             │ │   Product         │
├─────────────────────┤ ├───────────────────┤
│ - username: String  │ │ - name: String    │
│ - email: String     │ │ - description: String│
│ - password: String  │ │ - price: Money    │
├─────────────────────┤ ├───────────────────┤
│ + login()           │ │ + calculateDiscount()│
│ + changePassword()  │ │ + updateStock()   │
└─────────────────────┘ └───────────────────┘
```

```java
// Inheritance example
public abstract class BaseEntity {
    protected Long id;
    protected Date createdAt;
    protected Date updatedAt;
    
    public Long getId() { return id; }
    public Date getCreatedAt() { return createdAt; }
    public Date getUpdatedAt() { return updatedAt; }
}

// Subclass User
public class User extends BaseEntity {
    private String username;
    private String email;
    private String passwordHash;
    private Role role;
    
    public boolean authenticate(String password) {
        // Authentication logic
        return passwordHash.equals(hash(password));
    }
}

// Subclass Product
public class Product extends BaseEntity {
    private String name;
    private String description;
    private Money price;
    private Category category;
    
    public Money calculateDiscount(double percentage) {
        return price.multiply(1 - percentage / 100);
    }
}
```

### Polymorphism

Polymorphism allows objects of different types to be treated uniformly.

```java
// Polymorphism example
public interface PaymentProcessor {
    PaymentResult processPayment(Money amount);
}

public class CreditCardProcessor implements PaymentProcessor {
    @Override
    public PaymentResult processPayment(Money amount) {
        // Process credit card payment
        return new PaymentResult(true, "Payment successful");
    }
}

public class PayPalProcessor implements PaymentProcessor {
    @Override
    public PaymentResult processPayment(Money amount) {
        // Process PayPal payment
        return new PaymentResult(true, "Payment successful");
    }
}

public class PaymentService {
    private PaymentProcessor processor;
    
    public void setProcessor(PaymentProcessor processor) {
        this.processor = processor;
    }
    
    public PaymentResult pay(Money amount) {
        // Polymorphic call
        return processor.processPayment(amount);
    }
}
```

```java
// Activity diagram implementation
public class OrderWorkflow {
    public enum OrderState {
        RECEIVED, VALIDATED, PROCESSING, COMPLETED, CANCELLED
    }
    
    public class OrderProcess {
        public void processOrder(Order order) {
            // Action: Validate payment
            Payment payment = paymentService.validate(order.getPayment());
            
            // Decision: Check validation result
            if (!payment.isValid()) {
                // Action: Notify customer
                notificationService.sendPaymentFailed(order.getCustomer());
                return;
            }
            
            // Action: Check inventory
            InventoryResult inventory = inventoryService.checkAvailability(order);
            
            // Fork: Process items in parallel
            Parallel.parallel(() -> {
                // Action: Reserve items
                inventoryService.reserveItems(order);
            }, () -> {
                // Action: Process payment
                paymentService.process(order.getPayment());
            });
            
            // Join: Wait for both to complete
            Parallel.join();
            
            // Decision: Check inventory result
            if (inventory.isComplete()) {
                // Action: Process shipment
                shipmentService.ship(order);
            } else {
                // Action: Backorder
                inventoryService.createBackorder(order);
            }
            
            // Action: Generate confirmation
            confirmationService.send(order);
        }
    }
}
```

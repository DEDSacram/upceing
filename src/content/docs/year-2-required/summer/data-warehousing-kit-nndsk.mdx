## Week 1: DWH Introduction

A data warehouse (DWH) is a central analytical repository. Inmon's definition: *subject-oriented, integrated, time-variant, non-volatile* collection of data supporting management decisions.

### Key Concepts

#### 1. Four Defining Properties

- **Subject-oriented** — organised around business subjects (sales, customers), not applications.
- **Integrated** — consistent naming, codes, units across sources.
- **Time-variant** — history is kept; every fact carries a time context.
- **Non-volatile** — loaded data is rarely updated in place; new snapshots are appended.

#### 2. DWH vs Operational Database

| Aspect | Operational DB | Data Warehouse |
|--------|---------------|----------------|
| Purpose | Run daily business | Analyse history, decide |
| Data | Current, detailed | Historical, aggregated |
| Updates | Frequent CRUD | Bulk loads, appends |
| Users | Clerks, applications | Analysts, managers |

#### 3. Basic Building Blocks

- **Sources** — OLTP systems, files, APIs.
- **Staging area** — raw landing zone for cleansing.
- **Core DWH** — integrated, historised store.
- **Data marts** — subject-specific subsets for departments.
- **Consumers** — reports, OLAP cubes, dashboards, mining tools.

### Example: Grain Statement

```sql
-- Grain: one row per order line per day, amounts in CZK incl. VAT.
CREATE TABLE fact_sales_line (
    date_key     INTEGER NOT NULL,
    product_key  INTEGER NOT NULL,
    customer_key INTEGER NOT NULL,
    quantity     INTEGER NOT NULL,
    amount_czk   NUMERIC(12,2) NOT NULL,
    PRIMARY KEY (date_key, product_key, customer_key)
);
```

## Week 2: OLTP vs OLAP, ETL, BI

OLTP systems process transactions; OLAP systems analyse them. ETL/ELT moves data between the two worlds; Business Intelligence is the consuming layer.

### Key Concepts

#### 1. OLTP vs OLAP

| Aspect | OLTP | OLAP |
|--------|------|------|
| Query pattern | Many small reads/writes | Few large aggregations |
| Schema | Highly normalised (3NF) | Denormalised star/snowflake |
| Data volume per query | Tens of rows | Millions of rows |
| Optimisation | Indexes, locking, concurrency | Partitioning, bitmaps, cubes |

#### 2. ETL vs ELT

- **ETL** — Extract, Transform, Load. Transform before loading; classic for on-premise DWH.
- **ELT** — Extract, Load, Transform. Load raw data first, transform inside the target; common with cloud/lakehouse platforms.

#### 3. BI Stack and Data Mining Position

```
Sources → Staging → DWH → Data marts → BI (reports, OLAP, dashboards) → Decisions
                                              └→ Data mining (patterns, predictions)
```

### Example: OLTP vs OLAP Query

```sql
-- OLTP: single order lookup (fast, indexed).
SELECT order_id, status, total
FROM orders
WHERE order_id = 12345;

-- OLAP: monthly revenue by category (scan + aggregate).
SELECT d.month, p.category, SUM(f.amount_czk) AS revenue
FROM fact_sales_line f
JOIN dim_date d    ON d.date_key = f.date_key
JOIN dim_product p ON p.product_key = f.product_key
GROUP BY d.month, p.category
ORDER BY d.month;
```

## Week 3: DWH Architectures

Common topologies: two-tier (sources → DWH → marts), hub-and-spoke (Inmon), bus architecture with conformed dimensions (Kimball), and multidimensional (MOLAP/ROLAP/HOLAP) storage options.

### Key Concepts

#### 1. Inmon vs Kimball

| Aspect | Inmon (top-down) | Kimball (bottom-up) |
|--------|------------------|---------------------|
| Core | Normalised enterprise DWH | Dimensional marts first |
| Build order | DWH, then marts | Marts with conformed dims |
| Strength | Consistency, integration | Speed of delivery, usability |

#### 2. Storage Modes

- **MOLAP** — data in proprietary cubes; fast queries, costly rebuilds.
- **ROLAP** — data stays relational; flexible, relies on SQL optimisation.
- **HOLAP** — hybrid: aggregates in cubes, details relational.

#### 3. Multidimensional View

- **Dimensions** — analysis axes (time, product, region).
- **Measures** — numeric facts (revenue, quantity).
- **Hierarchies** — drill paths (year → quarter → month → day).

### Example: Conformed Dimension

```sql
-- One shared date dimension used by sales AND inventory marts.
CREATE TABLE dim_date (
    date_key   INTEGER PRIMARY KEY,
    full_date  DATE NOT NULL,
    year       SMALLINT NOT NULL,
    quarter    SMALLINT NOT NULL,
    month      SMALLINT NOT NULL,
    day        SMALLINT NOT NULL,
    is_weekend BOOLEAN NOT NULL
);
```

## Week 4: Star, Snowflake, Layers

The star schema puts one fact table at the centre with denormalised dimension tables around it. Snowflake normalises dimensions into sub-tables. Reporting layers separate raw, integrated, and presentation zones.

### Key Concepts

#### 1. Facts vs Dimensions

| Element | Content | Example |
|---------|---------|---------|
| **Fact** | Measures + foreign keys | `amount_czk`, `quantity` |
| **Dimension** | Descriptive attributes | product name, region |
| **Degenerate dim** | Operational number kept in fact | `order_number` |

#### 2. Star vs Snowflake

- **Star** — one table per dimension; fewer joins, more redundancy; preferred for query speed.
- **Snowflake** — dimensions normalised (product → subcategory → category); less redundancy, more joins.

#### 3. Layer Responsibilities

| Layer | Role |
|-------|------|
| Staging | Raw extracts, no business rules |
| Integration / core | Cleansed, conformed, historised |
| Presentation / marts | Star schemas, aggregates, report views |

### Example: Star Schema

```sql
CREATE TABLE dim_product (
    product_key INTEGER PRIMARY KEY,
    sku         VARCHAR(20) NOT NULL,
    name        VARCHAR(200) NOT NULL,
    category    VARCHAR(100) NOT NULL,
    brand       VARCHAR(100)
);

CREATE TABLE fact_sales (
    date_key    INTEGER NOT NULL REFERENCES dim_date(date_key),
    product_key INTEGER NOT NULL REFERENCES dim_product(product_key),
    quantity    INTEGER NOT NULL,
    amount_czk  NUMERIC(12,2) NOT NULL,
    PRIMARY KEY (date_key, product_key)
);

-- Snowflake variant: split category out.
CREATE TABLE dim_category (
    category_id   INTEGER PRIMARY KEY,
    category_name VARCHAR(100) NOT NULL
);
```

## Week 5: DWH Methodology

Methodology covers business requirements, source analysis, design, build, deployment, and operation. Skipping requirements or source profiling is the most common cause of DWH failure.

### Key Concepts

#### 1. Business Requirements

- Identify decisions, questions, KPIs, users, and refresh needs (daily? hourly?).
- Distinguish must-have vs nice-to-have facts and dimensions.
- Record data ownership and access rules.

#### 2. Source Data Analysis

- Inventory systems, tables, keys, codes, and data quality issues.
- Profile data: nulls, duplicates, formats, ranges.
- Decide historisation strategy: SCD Type 1 (overwrite), Type 2 (new row), Type 3 (previous-value column).

#### 3. Build and Operate

```
Requirements → Dimensional design → ETL design → Build → Test → Deploy → Monitor
```

### Example: SCD Type 2

```sql
-- Keep history of customer segment changes: new row per change.
CREATE TABLE dim_customer_scd2 (
    customer_sk  SERIAL PRIMARY KEY,   -- surrogate key
    customer_bk  VARCHAR(20) NOT NULL, -- business key
    segment      VARCHAR(50) NOT NULL,
    valid_from   DATE NOT NULL,
    valid_to     DATE,                 -- NULL = current
    is_current   BOOLEAN NOT NULL
);

-- Current view for reports.
CREATE VIEW v_dim_customer_current AS
SELECT * FROM dim_customer_scd2 WHERE is_current;
```

## Week 6: ETL and ELT Preparation

Data preparation means extracting from sources, cleansing, conforming, and deploying into the DWH. Typical steps: extract → validate → cleanse → deduplicate → conform → load, with logging and restartability.

### Key Concepts

#### 1. Extraction Patterns

- **Full load** — reload everything; simple, heavy.
- **Incremental / CDC** — load only changes via timestamps, flags, or log capture.
- **Trickle feed** — near-real-time micro-batches.

#### 2. Transformation Duties

- Type casts, code mapping, unit conversion, address standardisation.
- Surrogate key assignment, SCD handling, aggregate pre-computation.
- Quarantine of rejected rows with error codes.

#### 3. Deployment Concerns

- Idempotent loads (re-running is safe), load order (dimensions before facts).
- Row counts, checksums, and reconciliation reports after each run.

### Example: Staging + Cleansing

```sql
-- 1. Land raw extract.
CREATE TABLE stg_orders_raw (
    order_id   VARCHAR(20),
    order_date VARCHAR(20),   -- dirty format from CSV
    amount     VARCHAR(20)
);

-- 2. Cleanse into staging clean.
INSERT INTO stg_orders_clean (order_id, order_date, amount_czk)
SELECT
    TRIM(order_id),
    TO_DATE(TRIM(order_date), 'DD.MM.YYYY'),
    REPLACE(TRIM(amount), ',', '.')::NUMERIC(12,2)
FROM stg_orders_raw
WHERE TRIM(order_id) <> '' AND TRIM(amount) <> '';

-- 3. Quarantine rejects.
INSERT INTO stg_orders_reject (order_id, reason)
SELECT order_id, 'missing amount'
FROM stg_orders_raw
WHERE TRIM(amount) = '' OR amount IS NULL;
```

## Week 7: OLAP Analysis

OLAP operations navigate multidimensional data: slice (fix one dimension value), dice (sub-cube), drill-down/up (change hierarchy level), roll-up (aggregate), and pivot (rotate axes).

### Key Concepts

#### 1. Core Operations

| Operation | Meaning | Example |
|-----------|---------|---------|
| Slice | One value of a dimension | Year = 2026 |
| Dice | Range on several dims | Q1, categories A–C |
| Drill-down | More detail | Quarter → month |
| Roll-up | Less detail | Month → quarter |
| Pivot | Swap axes | Products to rows |

#### 2. Hierarchies and Levels

- Time: year → quarter → month → day.
- Geography: country → region → city → store.
- Product: category → subcategory → SKU.

#### 3. Query Pattern

- Large scans with `GROUP BY` over hierarchies; pre-aggregated summary tables speed up common levels.

### Example: Drill Path in SQL

```sql
-- Roll-up level: revenue by quarter.
SELECT d.year, d.quarter, SUM(f.amount_czk) AS revenue
FROM fact_sales f
JOIN dim_date d ON d.date_key = f.date_key
GROUP BY d.year, d.quarter
ORDER BY d.year, d.quarter;

-- Drill-down: same, but by month.
SELECT d.year, d.quarter, d.month, SUM(f.amount_czk) AS revenue
FROM fact_sales f
JOIN dim_date d ON d.date_key = f.date_key
GROUP BY d.year, d.quarter, d.month
ORDER BY d.year, d.quarter, d.month;
```

## Week 8: CUBE and ROLLUP in SQL

`ROLLUP`, `CUBE`, and `GROUPING SETS` produce subtotals and grand totals in one query. The `GROUPING()` function distinguishes real NULLs from subtotal rows.

### Key Concepts

#### 1. ROLLUP — Hierarchical Subtotals

- `GROUP BY ROLLUP (a, b, c)` generates totals for (a,b,c), (a,b), (a), and ().
- Order of columns matters: it follows the hierarchy left to right.

#### 2. CUBE — All Combinations

- `GROUP BY CUBE (a, b)` generates (a,b), (a), (b), and ().
- Use for cross-tab reports; more rows than `ROLLUP`.

#### 3. GROUPING SETS and GROUPING()

- `GROUPING SETS` lists exactly the groupings wanted.
- `GROUPING(col)` returns 1 on subtotal rows, 0 otherwise — use it for labels.

### Example: ROLLUP vs CUBE

```sql
-- ROLLUP: year > quarter subtotals + grand total.
SELECT d.year, d.quarter, SUM(f.amount_czk) AS revenue,
       GROUPING(d.year) AS g_year, GROUPING(d.quarter) AS g_q
FROM fact_sales f
JOIN dim_date d ON d.date_key = f.date_key
GROUP BY ROLLUP (d.year, d.quarter)
ORDER BY d.year, d.quarter;

-- CUBE: all combos of region x category.
SELECT r.region, p.category, SUM(f.amount_czk) AS revenue
FROM fact_sales f
JOIN dim_product p ON p.product_key = f.product_key
JOIN dim_region r  ON r.region_key = f.region_key
GROUP BY CUBE (r.region, p.category)
ORDER BY r.region, p.category;

-- Exact control with GROUPING SETS.
SELECT d.year, p.category, SUM(f.amount_czk) AS revenue
FROM fact_sales f
JOIN dim_date d ON d.date_key = f.date_key
JOIN dim_product p ON p.product_key = f.product_key
GROUP BY GROUPING SETS ((d.year, p.category), (d.year), ());
```

## Week 9: Integration Tools I — ODI

Oracle Data Integrator (ODI) is an ELT-style integration tool. Key ideas: topology (physical + logical architecture), models (source/target metadata), interfaces/mappings, packages, and scenarios for execution.

### Key Concepts

#### 1. Topology: Physical vs Logical

| Level | Content | Example |
|-------|---------|---------|
| Physical | Servers, schemas, agents | `PROD_ORACLE`, `STG_POSTGRES` |
| Logical | Abstract names used in mappings | `SRC_SALES`, `TRG_DWH` |
| Context | Binds logical to physical | DEV, TEST, PROD |

#### 2. Models and Datastores

- Reverse-engineer source/target structures into models.
- Datastores carry columns, keys, and constraints used by mappings.

#### 3. Interface / Mapping Anatomy

- Sources → joins/filters → expressions → target with loading knowledge module (LKM/IKM choice).
- Design once against logical schemas; execute in any context.

### Example: ODI-style Mapping Sketch

```sql
-- What an ODI mapping "sales -> fact_sales" does under the hood (ELT):
-- 1. Load raw into staging (C$ table), 2. transform inside target DB.
CREATE TABLE c$_fact_sales AS
SELECT TRIM(order_id) AS order_id, amount::NUMERIC(12,2) AS amount_czk
FROM src_orders;

INSERT INTO fact_sales (date_key, product_key, quantity, amount_czk)
SELECT d.date_key, p.product_key, s.qty, s.amount_czk
FROM c$_fact_sales s
JOIN dim_date d    ON d.full_date = s.order_date
JOIN dim_product p ON p.sku = s.sku;
```

## Week 10: Integration Tools II and Reporting

ODI packages chain mappings with variables, loops, and error handling; scenarios freeze a version for scheduling. Reporting tools then consume the presentation layer; ODV (Oracle Data Visualization / reporting) architecture separates data, semantic model, and visual layer.

### Key Concepts

#### 1. Packages and Scenarios

- **Package** — ordered steps: mappings, procedures, OS commands, e-mail on failure.
- **Scenario** — generated executable snapshot (versioned) for the scheduler/agent.
- **Load plans** — parallel/serial orchestration with restart points.

#### 2. Reporting Layers

| Layer | Role |
|-------|------|
| Physical | Tables, materialised aggregates |
| Semantic / business model | Friendly names, joins, calculations, security |
| Presentation | Folders per department, pre-built metrics |

#### 3. ODV / Reporting Principles

- One metric, one definition (certified KPIs in the semantic model).
- Parameterised, drillable reports; separate ad-hoc from certified content.
- Schedule heavy reports off-peak; cache aggregates.

### Example: Certified Metric View

```sql
-- Semantic-layer style view: single definition of "net revenue".
CREATE VIEW v_rep_net_revenue AS
SELECT d.year, d.month, p.category,
       SUM(f.amount_czk) AS net_revenue,
       SUM(f.quantity)   AS units
FROM fact_sales f
JOIN dim_date d    ON d.date_key = f.date_key
JOIN dim_product p ON p.product_key = f.product_key
GROUP BY d.year, d.month, p.category;
```

## Week 11: Visualisation and Dashboards

Good dashboards answer one business question per page, show KPIs with context (targets, trends), and keep the visual encoding honest. Common elements: KPI cards, trend lines, bar comparisons, maps, and filtered detail tables.

### Key Concepts

#### 1. Dashboard Design Rules

- <span class="badge">Good</span> One message per dashboard; 5-second rule (key insight visible immediately).
- <span class="badge danger">Bad</span> 3D pie charts, dual axes with different scales, rainbow colours.
- Always show comparison: vs target, vs prior period, or vs benchmark.

#### 2. Chart Selection

| Question | Chart |
|----------|-------|
| Trend over time | Line / area |
| Compare categories | Bar (horizontal for long labels) |
| Part of whole (few parts) | Stacked bar or donut |
| Distribution | Histogram / box plot |
| Geography | Choropleth map |

#### 3. Interactivity

- Global filters (year, region), drill from chart to detail, cross-highlighting.
- Separate exploratory (analyst) from executive (static KPI) dashboards.

### Example: KPI Query for a Dashboard

```sql
-- KPI: current vs previous month revenue + change %.
WITH m AS (
    SELECT d.year, d.month, SUM(f.amount_czk) AS revenue
    FROM fact_sales f
    JOIN dim_date d ON d.date_key = f.date_key
    GROUP BY d.year, d.month
)
SELECT cur.year, cur.month, cur.revenue AS revenue_now,
       prev.revenue AS revenue_prev,
       ROUND(100.0 * (cur.revenue - prev.revenue) / NULLIF(prev.revenue, 0), 1) AS pct_change
FROM m cur
LEFT JOIN m prev
  ON (prev.year * 12 + prev.month) = (cur.year * 12 + cur.month) - 1
ORDER BY cur.year DESC, cur.month DESC
LIMIT 6;
```

## Week 12: BI in Practice

BI in practice means governed self-service: certified datasets, KPI definitions, refresh SLAs, row-level security, and adoption tracking. Technology matters less than trust in numbers.

### Key Concepts

#### 1. Governed Self-Service

- IT owns certified models and refresh; business builds own reports on top.
- Promotion path: personal → team → certified.

#### 2. KPIs and SLAs

- Each KPI has owner, definition, grain, refresh cadence, and target.
- Monitor refresh jobs; alert on failure or stale data.

#### 3. Security and Adoption

- Row-level security (region managers see only their region).
- Track usage: which dashboards are opened, which are stale — retire unused ones.

### Example: Row-Level Security Pattern

```sql
-- Region managers see only their region (application predicate).
CREATE VIEW v_sales_my_region AS
SELECT f.*, r.region
FROM fact_sales f
JOIN dim_region r ON r.region_key = f.region_key
WHERE r.region = CURRENT_SETTING('app.current_region');

-- KPI with owner and target (documented alongside the view).
COMMENT ON VIEW v_sales_my_region IS 'Owner: Sales Controlling. Refresh: daily 06:00. Target: +5% YoY.';
```

## Week 13: Data Mining in Practice

Data mining finds patterns (segmentation, associations) and builds predictions (churn, demand) on top of the warehouse. Typical process: business goal → data prep → model → evaluate → deploy, with careful attention to data leakage and overfitting.

### Key Concepts

#### 1. Task Types

| Task | Question | Example method |
|------|----------|----------------|
| Classification | Which class? | Decision tree, logistic regression |
| Clustering | Which natural groups? | K-means |
| Association | What goes together? | Apriori (market basket) |
| Forecasting | How much next month? | Exponential smoothing, regression |

#### 2. Process (CRISP-DM in Brief)

1. Business understanding, 2. data understanding, 3. preparation, 4. modelling, 5. evaluation, 6. deployment.

#### 3. Pitfalls

- <span class="badge danger">Bad</span> Training on future data (leakage), judging by accuracy on imbalanced classes.
- Always hold out a test set; prefer confusion matrix / lift over raw accuracy.

### Example: Mining-Ready Mart + Scoring Sketch

```sql
-- Churn mart: one row per customer with behavioural features.
CREATE VIEW v_churn_features AS
SELECT c.customer_key,
       COUNT(DISTINCT f.date_key) AS active_days_90d,
       SUM(f.amount_czk)           AS revenue_90d,
       MAX(d.full_date)            AS last_purchase
FROM dim_customer_scd2 c
LEFT JOIN fact_sales f ON f.customer_key = c.customer_sk
LEFT JOIN dim_date d    ON d.date_key = f.date_key
WHERE c.is_current
GROUP BY c.customer_key;
```

## Code Review Guide

### What to Look For

1. **Correctness** — grain respected, keys consistent, no fan-out in joins.
2. **Completeness** — SCD handling, rejects quarantined, reconciliation counts.
3. **Performance** — partitioning, indexes, aggregate strategy for large facts.
4. **Readability** — named views, comments on business rules.

<div class="review-note">

<strong>🔍 Practice Review:</strong> A fact table joins to two dimensions but row counts triple. Likely causes: duplicate dimension keys, missing SCD filter (`is_current`), or a many-to-many join without a bridge table. Check `COUNT(*) GROUP BY key HAVING COUNT(*) > 1` on each dimension.

</div>
